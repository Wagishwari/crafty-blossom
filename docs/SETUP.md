# Supabase, payments and administrator setup

1. Create a dedicated Crafty Blossoms Supabase development project. Do not reuse DoctorOS or CAMPUSIQ. Confirm its project reference before applying SQL.
2. Use the Supabase CLI to initialise this project's local configuration if needed (`supabase init`), link to the selected project, and inspect its migration history and current tables. This implementation generated the migration using CLI 2.81.3, not by guessing a timestamp.
3. Review and apply `supabase/migrations/20261027131854_commerce_platform.sql` to the dedicated project using your normal migration workflow. Run the Supabase security/performance advisors afterward. Apply `supabase/seed.sql` only to load the actual owner-supplied products. Never load `tests/database.test.mjs` fixtures into a real project.
4. Configure Supabase Auth's site URL, allowed redirect URLs, email verification and verified SMTP sender. Include `/account/recovery` on the correct site origin. Disable open admin registration: customer registration never grants an admin role.
5. Copy server-only environment names from `.env.example`. For Vercel use its encrypted environment settings; for local Next.js use `.env.local`; for the preserved Worker preview use `.dev.vars`. `CHECKOUT_TOKEN_SECRET` and `CRON_SECRET` must each be generated independently with at least 32 cryptographically random characters. Do not paste keys into chat or commit them.
6. Create and verify an owner account through Auth. In the project's privileged SQL editor insert its exact UUID into `public.admin_profiles(user_id,role)` with role `admin`. Confirm an ordinary customer receives HTTP 403 from the admin API and cannot mutate administrator membership through the Data API.
7. Sign in at `/account`, then visit `/admin`. Load the real catalogue, confirm categories and images, add confirmed materials/care, create SKUs and variants, set prices in **paise**, then record actual stock via inventory adjustments. Unknown-price pieces should have no active variants and continue to say “Enquire to Order”. Sale prices require a lower positive value; discounts are never seeded.
8. Configure delivery zones using real supported PIN prefixes and actual charges/transit days. Express and scheduled options must remain off unless the studio can operationally support them. Configure production days per product; these are added to transit estimates. Enter approved business identity, invoice details and policies.
9. Configure a Razorpay **test** key pair and a distinct webhook signing secret. Subscribe to `payment.captured` and `refund.processed` at `/api/commerce/webhook`. The webhook must reach a public HTTPS staging URL. A local URL cannot receive provider webhooks directly. Verify callback and webhook signatures, duplicate delivery, failure/retry and expiry before considering live keys.
10. Configure Resend with an approved sender address/domain. Outbound email is queued in the database and only sent by the authenticated maintenance task. Confirm delivery and retry behavior with test recipients owned by the project team.
11. Schedule authenticated GET requests to `/api/commerce/cron` using `Authorization: Bearer <CRON_SECRET>` at least every 10 minutes. `vercel.json` contains the desired schedule, but plan eligibility must be checked before deployment; frequent Vercel Cron schedules may require a paid plan. No paid plan or external scheduler has been purchased or enabled. An existing supported scheduler can call the same protected endpoint instead. Do not deploy without a reliable maintenance schedule.
12. Review all launch checks in `LAUNCH.md`. Keep `ALLOW_LIVE_PAYMENTS=false`. Only after the staging checks and business approvals are complete should an owner set `LAUNCH_VALIDATED=true`, enable approved policies/commerce in the dashboard, and separately authorise live merchant keys.

The schema uses RLS on every business table. Customer reads are scoped to `auth.uid()` where directly permitted. Public and customer roles cannot execute stock/payment RPCs or write order totals. The application uses verified Auth users and checks `admin_profiles` server-side. It never trusts customer-editable user metadata for authorisation.

Private images are stored in the private `order-personalisation` bucket; short-lived signed links require the owner browser/account or an administrator. Public product images are in `brand-products`. File signatures, sizes and MIME types are checked; SVG and executable uploads are rejected. Configure rate-limit proxy headers only behind the deployment provider, and test the effective client IP behavior before launch.
